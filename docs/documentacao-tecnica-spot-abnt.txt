RESUMO
Esta documentação técnica do sistema Sistemas de Projetos, Organização e
Tarefas (SPOT) registra a arquitetura, as regras de negócio, o modelo de dados, os
contratos de API e as condições de operação do SPOT na versão consultada em 10
de novembro de 2026. O levantamento utiliza o código-fonte identificado por commit,
migrations, rotas, componentes e evidências automatizadas, sem tratar propostas
como recursos entregues. A aplicação emprega Laravel 13, React 18, PostgreSQL e
consolidação analítica com Python e pandas. São descritos provisionamento
administrativo e ativação por e-mail, controle de permissões, gerente obrigatório,
execução de projetos, finanças, agenda, notificações e chat com aprovador
escolhido. Também são registrados os modelos de e-mail em três idiomas, o tutorial,
os recursos de leitura e a tradução automática opcional de mensagens. A revisão
aprovou 256 testes de servidor com 3.487 asserções, inclusive em contêiner, e 36
suítes de navegador, além do build e das auditorias de dependências. A entrega
corresponde a código verificado para homologação e não a uma declaração de
produção liberada. Credenciais, domínio, integrações reais, responsáveis de
projetos antigos e revisão humana de acessibilidade permanecem como condições
de aceite. Referências atualizadas, inventários e o link da versão do repositório
permitem consultar os artefatos e reproduzir a avaliação.
Palavras-chave: gestão de projetos; aplicação web; controle de acesso; análise de
dados; testes de software.

ABSTRACT
This technical documentation records the architecture of SPOT (Sistemas de
Projetos, Organização e Tarefas), business rules, data structures, API contracts and
operational conditions for the source version examined on November 10, 2026. It
draws on the identified commit, migrations, routes, components and automated
evidence, without treating planned capabilities as delivered features. The application
uses Laravel 13, React 18, PostgreSQL, and analytical processing with Python and
pandas. It describes administrative provisioning, email-based activation, permissions,
required project ownership, project execution, finances, calendar, notifications and
chat with a selected approver. The documentation also covers three-language email
templates, the tutorial, reading adjustments and optional automatic message
translation. Verification passed 256 server tests with 3,487 assertions, including
container execution, and 36 browser suites, together with the frontend build and
dependency audits. The delivery represents code verified for acceptance testing,
rather than an unconditional production release. Credentials, domain setup, real
integrations, legacy ownership records and human accessibility review remain
acceptance conditions. Updated references, inventories and a source-version link
support consultation and reproducibility.
Keywords: project management; web application; access control; data analysis;
software testing.

3 ARQUITETURA E AMBIENTE TECNOLÓGICO
O SPOT organiza interface, interface de programação de aplicações (API),
regras de domínio e persistência no mesmo repositório, com responsabilidades
separadas. O navegador apresenta o estado e envia requisições; o servidor valida e
autoriza cada operação; classes de domínio e modelos implementam invariantes e
transações. A integração não depende de um servidor de inferência para executar
as funções centrais (Longo et al., 2026c).
3.1 Componentes e versões
A documentação oficial do Laravel descreve o ciclo de requisição e os
serviços de uma aplicação PHP: Hypertext Preprocessor (PHP); o React estrutura a
interface em componentes, enquanto o Vite fornece o servidor de desenvolvimento e
a construção dos recursos estáticos (Laravel, 2026; Meta Platforms, [20--]; Vite,
[20--]). As versões do produto são obtidas dos manifestos, lockfiles e verificações do
projeto, não da versão mais recente anunciada nos sites.

3.2 Banco relacional e concorrência
O PostgreSQL é a persistência única da versão final. Referências a SQLite na
monografia preliminar descrevem um estado anterior e foram retiradas da descrição
do sistema atual. As migrations definem evolução de tabelas e relacionamentos;
transações e bloqueios de linha protegem decisões, movimentações e alterações de
equipe. A documentação PostgreSQL fundamenta o uso de integridade e controle
transacional (PostgreSQL Global Development Group, 2026).
Na alteração de equipe, um bloqueio no registro do projeto serializa
operações que poderiam remover simultaneamente os últimos responsáveis. No
chat, o par de usuários é representado por uma conversa e os pedidos pendentes
são conferidos sob transação. Esses controles sustentam o comportamento
verificado nos testes; não constituem, por si, um ensaio de escalabilidade (Longo et
al., 2026c).
3.3 Comunicação e implantação
A aplicação principal utiliza JavaScript Object Notation (JSON) e rotas
versionadas sob /api/v1, com sessão, cookies e proteção Cross-Site Request
Forgery (CSRF) nas operações mutáveis. A compatibilidade por token e o estoque
utilizam JSON Web Token (JWT) em suas rotas. OAuth conecta provedores

12
externos; sua homologação requer credenciais e permissões reais. Falhas de
validação são apresentadas próximas aos formulários e não devem expor Structured
Query Language (SQL), traces ou segredos.
O Docker Compose descreve serviços e volumes da aplicação (Docker,
2026). O empacotamento do SPOT inclui web, worker e scheduler, além do
PostgreSQL. E-mails usam a fila emails; atividades e limpezas periódicas são
agendadas dentro do processo PHP. O arquivo .env e dados de usuários não
integram a imagem (Longo et al., 2026c).

4.2 Identidade, convite e primeiro acesso
O primeiro acesso é iniciado por provisionamento administrativo. O link utiliza
token com hash persistido, validade e controle de uso. A identificação da ativação
compara somente o e-mail com a conta associada ao convite, desconsiderando
caixa e espaços nas extremidades; não exige que o nome digitado coincida com o
cadastro. O nome administrativo é preservado. Quando o e-mail diverge, a interface
orienta: Por gentileza, insira o e-mail correspondente ao do convite enviado! A
validade do token e a confirmação da senha continuam obrigatórias.
Uma nova entrada da conta em aguardando ativação revoga links anteriores
ainda não usados, cria outro token e agenda a mensagem após confirmar a
transação. A validade da ativação administrativa é de 48 horas. Edição de cargo ou
perfil de uma conta já pendente não é um novo evento de reenvio. A recuperação de
senha é um fluxo diferente: o link vale 60 minutos e há intervalo de 60 segundos
entre gerações para a mesma conta (Longo et al., 2026c).
4.3 Projetos, equipe e execução
O cadastro v1 exige gerente do projeto elegível. O usuário selecionado entra
na equipe como manager, sem duplicação se também constar na seleção inicial.
Equipes, atribuições e remoções de membros preservam ao menos um gerente ativo
elegível, sincronizando o campo de referência quando necessário. Perfis de
administrador, gerente administrador e gerente podem ser elegíveis para a função,
conforme as regras do servidor.
Projetos concentram contrato, situação, datas, membros e planejamento.
Tarefas oferecem visualizações de trabalho e apontamentos; tarifas possuem
vigência, e despesas passam por revisão. Finalização e reabertura seguem
autorização e preservação do histórico. O módulo de documentos mantém suas
regras de privacidade: associar um arquivo a projeto ou tarefa não equivale a
compartilhá-lo com toda a equipe (Longo et al., 2026c).

16
4.4 Chat e aprovação direcionada
O chat é individual e restrito à empresa atual. Há acesso direto quando os
dois usuários possuem participação ativa, não revogada, com papel analyst ou
manager em um mesmo projeto. Fora desse vínculo, o formulário solicita pessoa,
motivo e o destinatário em Enviar aprovação para. A lista contém administradores e
gerentes administradores ativos e elegíveis da mesma empresa, excluindo o
solicitante; podem estar fora do projeto.
O campo assigned_reviewer_id registra quem recebeu o novo pedido;
reviewer_id registra quem decidiu. Somente o escolhido recebe o aviso e pode
aprovar ou recusar. A autorização vale para o par, e não libera a leitura de
conversas de terceiros. Pedidos antigos sem atribuição mantêm compatibilidade
com o fluxo anterior. Uma pendência por par impede duplicação, inclusive em
sentido inverso; pedidos recusados ou revogados permitem nova tentativa conforme
a elegibilidade (Longo et al., 2026c).
Apenas o autor pode editar uma mensagem, até 24 horas do envio original.
As revisões são preservadas e uma versão é conferida para evitar sobrescrita
concorrente. Anexos usam acesso autorizado e descrições de imagem podem ser
informadas. O editor fornece formatação e atalhos; Enter envia e Ctrl + Shift + Enter
insere nova linha. A existência de autorização de revisão não concede acesso ao
conteúdo de uma conversa alheia.

4.5 Agenda, notificações e e-mails
A agenda reúne eventos internos e conexões externas disponíveis. Grupos,
participantes, fuso e detalhes são validados. As notificações consideram
preferências por canal, silêncio, frequência e deduplicação. Resumos diários ou
semanais e envios imediatos são processados em lotes e filas, com tratamento de
falha e nova tentativa (Longo et al., 2026c).
Ativação, convite, recuperação e notificações compartilham o layout de
correio: cabeçalho Spot, título, ação, link alternativo e rodapé, com alternativa em
texto simples. Textos de estrutura possuem pt/en/es; dados escritos por pessoas
são preservados e escapados no HTML. Disponibilidade de Simple Mail Transfer
Protocol (SMTP), reputação do remetente e apresentação em clientes de e-mail
reais exigem homologação separada.

4.6 Portfólio e processamento analítico
Os relatórios consolidam situação, custos, receitas, margens, horas e
despesas, usando processos Python com pandas. A biblioteca fornece estruturas e
operações de análise de dados (Pandas Development Team, 2026). No SPOT, os
cálculos dependem dos registros e permissões existentes; falta de tarifa ou base de
cálculo não é convertida automaticamente em evidência de lucro ou desempenho.
Painéis permitem indicadores e diferentes visualizações, agregações e
exportação CSV. Resultados parciais são identificados. Uma falha do detalhamento
financeiro é tratada localmente sem cobrir todos os outros indicadores com uma tela
global de erro. O resultado financeiro é gerencial, depende da qualidade dos dados
e não equivale a demonstração contábil auditada (Longo et al., 2026c).
4.7 Idiomas, acessibilidade e tutorial
A interface dispõe de português, inglês e espanhol, ajustes de fonte, escala e
tema, indicação de foco e respeito à redução de movimento e cores forçadas. O
objetivo de acessibilidade é Web Content Accessibility Guidelines (WCAG) 2.2 nível
AA, referência que abrange diferentes necessidades de uso; resultados
automatizados não substituem avaliação humana nem certificam conformidade
integral (World Wide Web Consortium, 2024).
O tutorial é opcional e seleciona as etapas conforme permissões e
disponibilidade do chat. Explica navegação, projetos, execução, segurança e
solicitações, sem enviar formulários de negócio. A mudança de idioma dentro do
passeio não grava alterações na conta. A posição dos destaques é verificada para
telas disponíveis e áreas restritas. Nomes e conteúdos pessoais usam marcação
para impedir tradução automática da interface (Longo et al., 2026c).
4.8 Tradução automática e escopo de IA
As bandeiras no cabeçalho da conversa escolhem apenas o destino da
tradução da mensagem, sem alterar o idioma global. O texto traduzido é
apresentado no balão, identificado como automático, com acesso ao original. A

19
integração opcional usa o endpoint de tradução do LibreTranslate (LibreTranslate,
[20--]). Credenciais e endereço do serviço permanecem no servidor.
É necessário distinguir tradução automática de agentes de planejamento ou
geração de conteúdo. A versão final não demonstra um agente generativo para
estimar projetos, redistribuir equipes ou tomar decisões gerenciais. Automação de
notificações, regras determinísticas e consolidação com pandas também não são,
por si, implementação de inteligência artificial. A pesquisa de tecnologias de IA é
referência de possibilidades, não prova de entrega dessas funções.

5.1 Vínculos e integridade
Uma empresa limita as contas e os projetos visíveis. Projetos relacionam
responsáveis e membros; tarefas, horas e despesas referenciam o contexto de
execução. Conversas representam um par ordenado de usuários, enquanto

21
solicitações, mensagens, revisões e anexos mantêm relações separadas. Tokens de
acesso não são armazenados em texto simples. O responsável escolhido para
aprovação não é confundido com o usuário que concluiu a decisão.
A preservação do histórico é parte do domínio: revogar autorização não
remove mensagens; finalização limita operações sem apagar a trajetória do projeto;
exclusão de registros com dependências segue restrições e regras aplicáveis. A
normalização lógica evita repetir a mesma credencial, perfil ou estado em entidades
sem necessidade, embora haja snapshots controlados para rastreabilidade de
valores e decisões.
5.2 Contratos e erros
O inventário exportado pelo Laravel contém 170 rotas no ambiente
consultado, incluindo infraestrutura e framework. Esse total não representa 170
funcionalidades de negócio. O apêndice discrimina rotas da aplicação e o manifesto
preserva o critério de extração.
Respostas de validação usam a estrutura errors e os códigos Hypertext
Transfer Protocol (HTTP) compatíveis com o problema. Requisições sem
autorização, recursos não visíveis, conflito de estado e indisponibilidade têm
tratamentos distintos. O cliente de sessão inicializa CSRF antes das mutações e só
publica eventos de atualização após sucesso; logout não dispara recarga automática

7 IMPLANTAÇÃO E CONTINUIDADE
A entrada em operação depende do ambiente de destino e da homologação
das integrações. Esta seção organiza os requisitos de configuração, validação e
manutenção.
7.1 Preparação e configuração
A implantação proposta usa Docker Compose com serviços web, worker,
scheduler e PostgreSQL. O domínio precisa apontar para o servidor e o proxy
depende de condições reais para emitir HTTPS. O arquivo .env.production é
preenchido a partir do modelo; APP_KEY e JWT_SECRET devem ser configuradas
e preservadas nas atualizações. A chave JWT é necessária para o estoque e a
autenticação por token. Segredos não integram o Git nem os documentos de
consulta.
O build inclui os arquivos estáticos, dependências PHP de produção e
ambiente Python para os relatórios. Backups, uploads locais, evidências de
testes, .env e public/hot são excluídos do artefato. Uploads reais permanecem nos
volumes de armazenamento. Migrations são aplicadas após backup e revisão; o
seed da conta inicial não deve ser executado como rotina de atualização (Longo et
al., 2026c).
7.2 Validação do servidor de destino
O verificador scripts/check-production.php é somente leitura: verifica
ambiente, debug, origem HTTPS, cookies, chaves, correio configurado, existência
de assets, diretórios graváveis e conexão/migrations. Sua saída não expõe
credenciais nem envia mensagens. Mesmo com saída zero, é necessária a
homologação externa e a conferência dos responsáveis nos dados transferidos.
A revisão local identificou três projetos antigos sem o campo de gerente do
projeto preenchido, embora todos possuíssem gerente ativo na equipe. Não houve
escolha automática de responsáveis. Esse achado refere-se ao conjunto local
revisado e deve ser reavaliado na base que será implantada; não é uma
característica fixa do software.

26
7.3 Operação e manutenção
Workers devem consumir emails e default, e o scheduler deve ser executado
por minuto. Há controles de nova tentativa e consulta de falhas. Backups devem
incluir banco e arquivos, com restauração efetivamente testada. Uma mudança de
chave pode afetar dados e jobs criptografados; atualizar a aplicação não exige
substituir as chaves existentes.
A manutenção deve preservar rastreabilidade entre alteração, teste,
documentação e release. A equipe ainda precisa concluir a validação humana de
acessibilidade, os testes com provedores reais e a observação sob carga de uso. O
custo de infraestrutura, correio, manutenção e suporte continua existindo; ausência
de uma assinatura de software de terceiros não significa operação sem custos.
